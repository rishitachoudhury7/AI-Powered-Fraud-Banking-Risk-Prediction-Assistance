# AI Fraud Investigation & Banking Risk Compliance Assistant

An AI-powered assistant that investigates bank transactions for signs of fraud — combining a trained machine learning model, explainable AI, a rules engine, and a large language model that writes up its findings like a compliance analyst would.

**🔗 Try it live:**  https://rishitachoudhury7-fraud-detection-dashboard-hqxcnk.streamlit.app/ 

> The backend is hosted on a free server, so the first request after a while of inactivity may take 2-3 mins to respond while it wakes up. After that, it runs normally.

---

## What it does

You give it a transaction (or a chain of connected transactions), and it tells you:
- **How likely it is to be fraud**, based on a trained ML model
- **Why the model thinks that**, using SHAP to show which details of the transaction mattered most
- **Any red flags** it noticed, like an account being emptied out or money moving to a suspicious destination
- **Similar past cases** it found by searching a small library of fraud case studies
- **A written summary and recommendation**, generated by an LLM that's been given all of the above as evidence — so it explains its reasoning instead of just guessing

For a *chain* of transactions (say, money moving through two or three accounts), it can also catch patterns that only show up when you look at the whole sequence — like money briefly passing through an account and immediately being cashed out, or funds going in a circle and coming back to where they started.

---

## How it's put together

```
Transaction(s)
     │
     ▼
Machine learning model → fraud probability
     │
     ▼
SHAP → explains which details influenced that score
     │
     ▼
Rules engine → checks for known fraud patterns
     │
     ▼
Similar case search → finds matching historical examples
     │
     ▼
LLM → writes a final verdict and explanation, grounded in everything above
     │
     ▼
Dashboard → where you see it all
```

**One thing worth knowing:** the final verdict you see isn't just the raw model score — it's the LLM's judgment after weighing the model, the rules, and similar past cases together. The dashboard shows both the model's own score *and* the final verdict side by side, so if they ever disagree, you can see that clearly instead of it being hidden.

## The model

- A trained XGBoost model, built on top of over 6 million transaction records
- Performs strongly on held-out test data (PR-AUC of 0.97)
- Comes with SHAP explainability, so every prediction can be broken down into "why"

**A limitation worth being upfront about:** the model looks at each transaction on its own — it doesn't know about the account's history or other connected transactions. That's actually the reason the rules engine and chain investigation feature exist: to catch things the model structurally can't see by itself. In testing, a transaction that was part of a known fraud pattern scored under 8% from the model alone — but the rules engine caught it, and the final verdict correctly flagged it as high risk.

## What it can catch

**Looking at a single transaction:**
- An account being fully emptied out
- A transaction that's nearly the entire balance of the account
- Money moving to an account that shows no change (a sign of a "mule" account passing money through)
- Unusually large cash-outs or transfers
- A transaction happening shortly after account details were changed
- The first time an account does a certain type of transaction, especially right after a detail change

**Looking at a chain of transactions:**
- Money moving in, then immediately being cashed out
- Several similar-sized transactions that might be splitting up a larger amount to avoid detection
- Money going in a circle — from one account to another and back again
- A transaction where the currency paid doesn't match the currency received
- One account showing up in several transactions in a short chain

**One safeguard we added:** the system only lets rule flags override a low model score if at least *two* independent flags agree — a single weak signal isn't enough on its own. This was added after noticing the assistant was flagging too many ordinary transactions as risky; testing against a batch of everyday, harmless transactions confirmed it fixed the issue.

---

## How it finds similar past cases

There's a small library of fraud case studies (written as realistic examples, not real customer data). Each one is turned into a numerical representation and stored in a database that supports similarity search. When a new transaction comes in, the system searches this library for the closest matches and hands them to the LLM — so instead of reasoning from general knowledge, it can say something like "this looks like Case 003" and explain why.

## A few things I ran into while building this

- **Fairness consideration:** some of the source data included fields like gender and nationality. I deliberately left these out of both the model and the rules — using them would raise real fairness and discrimination concerns in an actual banking context, and leaving them out doesn't cost the system any real detection power.
- **A tricky bug:** for a while, the similar-case search was silently returning nothing, with no error message. After a lot of digging, it turned out to be a mismatched search index — configured for a much larger dataset than what was actually there. Fixing the index setup solved it.
- **A hosting constraint:** the original approach for generating embeddings used a fairly heavy library that didn't fit in the free hosting tier's memory limit. Switching to a hosted embedding API instead solved it, at the small cost of a bit of extra response time.
- **Being honest about disagreement:** rather than quietly picking one signal over another when the model, the rules, and the similar-case search disagree, the system shows all of them — so it's clear when and why the AI's final answer overrides the raw model score.

## What could be improved next

- Teaching the model itself to recognize account-level patterns (like transaction frequency or account age), not just relying on the rules engine for that
- More advanced pattern detection for fraud rings or multi-account laundering, beyond simple back-and-forth cycles
- Checking whether the model's confidence scores are well-calibrated against real-world fraud rates, rather than relying on fixed cutoffs

---

## A note on the data

This project uses synthetic and made-up transaction data, along with fraud case studies written for illustration rather than pulled from real records. It's a personal/portfolio project, not connected to any real bank or real customer information, and isn't meant to be used for actual financial decisions as-is.
